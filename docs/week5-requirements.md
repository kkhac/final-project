# კვირა 5 — პრომპტ ტესტირების მოთხოვნები და გამოყენების სცენარები

**პროექტი:** LLM Prompt and Conversational Regression Testing Platform  
**ავტორი:** ბარბარე ჯანაშვილი  
**მოდული:** Prompt Management და Rule-based Evaluation  

---

## 1. მიზანი

წინამდებარე დოკუმენტი განსაზღვრავს Prompt Management მოდულის გამოყენების სცენარებს (Use-case), მიღების კრიტერიუმებს და ვერსიონირების მოთხოვნებს. იგი წარმოადგენს სპეციფიკაციის საბაზისო დოკუმენტს მე-7–10 კვირის განხორციელებისთვის.

---

## 2. პრომპტ ტესტირების გამოყენების სცენარები

### UC-01 — ახალი პრომპტის შექმნა
**მოქმედი პირი:** დეველოპერი / პრომპტ ინჟინერი  
**მიზანი:** სისტემაში ახალი სისტემური პრომპტის შენახვა პირველი ვერსიის ჩათვლით.  
**წინაპირობა:** მომხმარებელი იმყოფება Prompt Management გვერდზე.  
**ძირითადი ნაკადი:**
1. მომხმარებელი შეიყვანს პრომპტის სახელს, სურვილისამებრ აღწერას და სისტემური პრომპტის ტექსტს.
2. სისტემა ქმნის `Prompt`-ის ჩანაწერს და ავტომატურად ქმნის `PromptVersion v1`-ს, სადაც `notes = "Initial version"`.
3. სისტემა აბრუნებს შექმნილ პრომპტს მისი ვერსიების სიასთან ერთად.

**მიღების კრიტერიუმები:**
- ყოველ ახლად შექმნილ პრომპტს შექმნისთანავე უნდა ჰქონდეს მინიმუმ ერთი ვერსია.
- `version_number` იწყება 1-დან.
- `name` სავალდებულოა; `description` — სურვილისამებრ.

---

### UC-02 — არსებულ პრომპტზე ახალი ვერსიის დამატება
**მოქმედი პირი:** დეველოპერი / პრომპტ ინჟინერი  
**მიზანი:** გაუმჯობესებული ან შეცვლილი სისტემური პრომპტის ახალ ვერსიად შენახვა ძველის დაკარგვის გარეშე.  
**წინაპირობა:** არსებობს პრომპტი მინიმუმ ერთი ვერსიით.  
**ძირითადი ნაკადი:**
1. მომხმარებელი ირჩევს არსებულ პრომპტს და შეიყვანს ახალ `system_prompt`-ის ტექსტს და სურვილისამებრ `notes`-ს.
2. სისტემა გამოთვლის `next_version = max(არსებული ვერსიების ნომრები) + 1`.
3. სისტემა ინახავს ახალ `PromptVersion`-ს მშობელ პრომპტთან დაკავშირებულს.

**მიღების კრიტერიუმები:**
- ვერსიების ნომრები ყოველთვის მზარდი (monotonically increasing) უნდა იყოს.
- ვერსიის წაშლა არ უნდა იწვევდეს ნუმერაციის გადატვირთვას ან განმეორებას (`max()` სტრატეგია, არა `len()` სტრატეგია).
- ახალი ვერსიის დამატებისას ძველი ვერსიები არ იცვლება და არ იშლება.

---

### UC-03 — პრომპტის ისტორიის ნახვა
**მოქმედი პირი:** დეველოპერი / ტესტერი  
**მიზანი:** პრომპტის ყველა ვერსიის ქრონოლოგიური თანმიმდევრობით ნახვა.  
**წინაპირობა:** პრომპტი არსებობს მრავალი ვერსიით.  
**ძირითადი ნაკადი:**
1. მომხმარებელი ითხოვს კონკრეტული პრომპტის ვერსიების სიას.
2. სისტემა აბრუნებს ვერსიებს `version_number`-ის მიხედვით ზრდადი თანმიმდევრობით დალაგებულს.

**მიღების კრიტერიუმები:**
- პასუხი ყოველთვის დალაგებულია `version_number ASC` მიხედვით.
- თითოეული ვერსია შეიცავს: `id`, `version_number`, `system_prompt`, `notes`, `is_active`, `created_at`.

---

### UC-04 — პრომპტის მეტამონაცემების განახლება
**მოქმედი პირი:** დეველოპერი  
**მიზანი:** პრომპტის სახელის ან აღწერის შეცვლა ვერსიებზე ზემოქმედების გარეშე.  
**ძირითადი ნაკადი:**
1. მომხმარებელი გზავნის PATCH მოთხოვნას განახლებული `name`-ით და/ან `description`-ით.
2. სისტემა ანახლებს მხოლოდ მითითებულ ველებს (ნაწილობრივი განახლება).
3. ვერსიები უცვლელი რჩება.

**მიღების კრიტერიუმები:**
- ამ endpoint-ის მეშვეობით მხოლოდ `name` და `description` ექვემდებარება რედაქტირებას.
- `system_prompt`-ის ცვლილება უნდა განხორციელდეს ვერსიონირების პროცედურით (UC-02).

---

### UC-05 — პრომპტის წაშლა
**მოქმედი პირი:** დეველოპერი  
**მიზანი:** პრომპტის და მისი ყველა ვერსიის სისტემიდან სრულად წაშლა.  
**ძირითადი ნაკადი:**
1. მომხმარებელი გზავნის DELETE მოთხოვნას პრომპტის ID-ით.
2. სისტემა წაშლის პრომპტს და ყველა მასთან დაკავშირებულ ვერსიას (cascade delete).
3. სისტემა აბრუნებს `204 No Content`.

**მიღების კრიტერიუმები:**
- Cascade წაშლა ვალდებულია წაშალოს ყველა შვილობილი `PromptVersion` ჩანაწერი.
- წაშლილი პრომპტის GET მოთხოვნა უბრუნებს `404`-ს.

---

### UC-06 — კონკრეტული ვერსიის წვდომა
**მოქმედი პირი:** დეველოპერი / შემფასებელი  
**მიზანი:** პრომპტის ზუსტი ვერსიის მოძიება ID-ით (გამოიყენება evaluation engine-ის მიერ ტესტის გაშვებისას).  
**მიღების კრიტერიუმები:**
- არასებული `version_id`-ის მოთხოვნა ვალიდური `prompt_id`-ის ქვეშ უბრუნებს `404 {"detail": "Version not found"}`.
- სხვა პრომპტის `version_id`-ის მოთხოვნაც `404`-ს უბრუნებს.

## 3. შეფასების კრიტერიუმები

როდესაც პრომპტის ვერსია LLM-ზე ტესტირდება, პასუხი ფასდება ორი დეტერმინისტული კრიტერიუმით:

| კრიტერიუმი | მეთოდი | გავლის პირობა |
|------------|--------|--------------|
| საკვანძო სიტყვების არსებობა | რეგისტრისადმი გაუმგრძნობელი substring-ის შემოწმება | ყველა მოსალოდნელი საკვანძო სიტყვა პასუხში გვხვდება |
| ფორმატის შესაბამისობა | Regex pattern-ის შემოწმება | `re.search(pattern, response)` დადებით შედეგს იძლევა |

**დამატებითი დაცვა:** ცარიელი ან მხოლოდ სფართოებისგან შემდგარი LLM-ის პასუხი ავტომატურად ვერ გადის ორივე კრიტერიუმს, ხოლო `rule_details`-ში `empty_response: true` მნიშვნელობა ფიქსირდება.

**Rule-based შემოწმების გამოსავლის სტრუქტურა:**
```json
{
  "expected_keywords": ["თანხის დაბრუნება", "პოლიტიკა"],
  "matched_keywords": ["თანხის დაბრუნება"],
  "missing_keywords": ["პოლიტიკა"],
  "empty_response": false,
  "regex_pattern": "^ძვირფასო მომხმარებელო",
  "regex_match": false
}
```

## 4. ვერსიონირების მოთხოვნები

| მოთხოვნა | გადაწყვეტილება |
|----------|---------------|
| ვერსიების ნუმერაციის სტრატეგია | `max(არსებული) + 1` — უსაფრთხოა ხარვეზების მიმართ, რომლებიც წაშლით შეიძლება წარმოიშვას |
| პირველი ვერსიის შექმნა | ავტომატური პრომპტის შექმნისას, `notes = "Initial version"` |
| ვერსიის უცვლელობა | შექმნის შემდეგ ვერსიის `system_prompt` ვეღარ ირედაქტირება |
| Active flag | `is_active` ველი დარეზერვებულია მომავალი გააქტიურების/გამორთვის ლოგიკისთვის |
| დალაგების თანმიმდევრობა | ყოველთვის `version_number ASC` მიხედვით ბრუნდება |
| Cascade წაშლა | პრომპტის წაშლისას ყველა მისი ვერსია იშლება |

## 5. API Endpoint-ების შეჯამება

| მეთოდი | გზა | დანიშნულება |
|--------|-----|------------|
| POST | `/prompts/` | პრომპტის + პირველი ვერსიის შექმნა |
| GET | `/prompts/` | ყველა პრომპტის სია |
| GET | `/prompts/{id}` | პრომპტის მიღება ვერსიებთან ერთად |
| PATCH | `/prompts/{id}` | სახელის/აღწერის განახლება |
| DELETE | `/prompts/{id}` | პრომპტის + ყველა ვერსიის წაშლა |
| GET | `/prompts/{id}/versions` | ვერსიების სია (დალაგებული) |
| POST | `/prompts/{id}/versions` | ახალი ვერსიის დამატება |
| GET | `/prompts/{id}/versions/{vid}` | კონკრეტული ვერსიის მიღება |

## 6. კვირა 5-ის ფარგლებს მიღმა (გადავადებული)

შემდეგი ფუნქციონალი გათვალისწინებულია მოგვიანებელ კვირებში:
- პრომპტის რედაქტირებისა და ვერსიების ისტორიის Frontend UI (კვირა 8)
- LLM-ის გაშვება პრომპტის ვერსიაზე (კვირა 10+)
- სემანტიკური შეფასება (LLM-as-a-Judge) (კვირა 11)
- ვერსიების გვერდ-გვერდ (Side-by-side) შედარების UI (კვირა 12)
